#+title: t3-code.el

An Emacs client for the T3 Code server, in the spirit of [[https://github.com/dnouri/pi-coding-agent][pi-coding-agent]]: a
rendered Markdown chat buffer for the conversation, an ordinary Emacs buffer
below it for the next message, and the current project as the starting point.

* Status

- versioned NDJSON bridge protocol (=t3 client --stdio=), one shared process
  and state store per environment, reference-counted subscriptions, sequence
  repair and bounded input handling
- project-first entry, a ledger of all threads, a switcher, resume and search
- a live chat transcript with Markdown and diff fontification, inline tool
  blocks with previews, folding, file/URL visiting and paged older history
- an input buffer with send/queue/steer/abort, prompt history, completion of
  slash commands, skills, project files and paths, and a pi-style header
- new threads (project root or worktree), forks, answers to agent questions,
  queued-message management, rename/pin/archive/delete, model and reasoning
  effort selection, notifications

SSH/TRAMP environments, relay/DPoP, credential persistence, terminals, diffs
per turn and pull requests remain later milestones.

* Setup

Add this checkout to =load-path= and connect to a local server:

#+begin_src emacs-lisp
(require 't3-code)
(defalias 't3 't3-code)
#+end_src

=M-x t3-code= expects a =t3= build containing =t3 client --stdio= in
=exec-path=.  To use the adjacent source checkout rather than an installed
=t3=, configure the version-matched bridge:

#+begin_src emacs-lisp
(setq t3-code-bridge-command
      (list "node" (expand-file-name "../t3code/apps/server/src/bin.ts"
                                     "/path/to/emacs-t3-code/")
            "client" "--stdio"))
#+end_src

Credentials live in =auth-source=, Emacs's canonical credential store
(=~/.authinfo.gpg= by default, or the system keyring via =auth-sources=).
Issue a reusable bearer token on the server host:

#+begin_src sh
t3 auth session issue --label emacs --token-only
#+end_src

The first =M-x t3-code= asks for it and, once the server has accepted it,
offers to save it as:

#+begin_example
machine 127.0.0.1 port 3773 login t3-code password BEARER-TOKEN
#+end_example

Later connections use it without asking.  A rejected stored token is
reported; update or remove its entry and reconnect.  To be asked every time
instead, set =t3-code-token= to =ask= (with =t3-code-token-type= =pairing=
for one-time tokens from =t3 auth pairing create=).  A string value is used
as is (Customize may write it to disk), and nil inherits
=T3_CLIENT_PAIRING_TOKEN= / =T3_CLIENT_ACCESS_TOKEN=.
=M-x t3-code-connect-prompt= connects to another URL with an explicit token.

=M-x t3-code-demo= opens the ledger against the deterministic fake bridge in
=bridge/fake-t3e.mjs=.

* Everyday workflow

=M-x t3-code= opens the conversation of the project containing
=default-directory=: the thread whose worktree you are in, otherwise the
project's most relevant active thread (working, then unseen, then most
recent).  Without one it offers to start a thread.  Outside known projects,
or with =C-u=, it opens the ledger.  Run again from a T3 buffer, it restores
the chat and input windows and focuses the input; =M-x t3-code-toggle= hides
them.

The chat buffer is on top and the input buffer below.  Type in the input and
press =C-c C-c= to send.  While the thread is working, =C-c C-c= queues the
message as a follow-up; =C-c C-s= steers the running turn instead and
=C-c C-k= aborts it.

The input header shows the model (click to change), reasoning effort (click
to cycle), activity phase, context usage, thread title, runtime mode, queued
messages and a global indicator of working (⚙) and newly finished (✓) threads
that opens the ledger.

** Composing

The input buffer is plain text: use the kill ring, macros, registers and
spell checking as usual.  =TAB= / =completion-at-point= completes:

- =/command= at the start of the message: the provider's slash commands
- =$skill= anywhere: the provider's skills
- =@path=: project files found by the server
- =./=, =../=, =~/= and absolute paths: local files

=M-p= / =M-n= (also =C-<up>= / =C-<down>=) recall sent prompts, =C-r= picks
one with completion, and =M-<next>= / =M-<prior>= scroll the chat without
leaving the input.  Drafts survive hiding the window; they last for the
buffer's lifetime.  Set =t3-code-input-window-display= to =on-demand= to hide
the input after each send, or =hidden= to open it only when composing.

** Reading

Each turn starts with a =You= heading followed by the =Assistant= section.
Answers and plans render as Markdown (=gfm-mode= from markdown-mode when
installed, otherwise =markdown-ts-mode=) with markup hidden (see
=t3-code-markdown-hide-markup=); file changes render as diffs.  Code blocks
are highlighted only with major modes Emacs already associates with file
names, and without running their mode hooks, so agent output cannot enable
arbitrary modes.  Tool calls appear inline as =$ command=, =edit path=,
=search …=; their output is collapsed to =t3-code-tool-preview-lines= lines.
Reasoning is shown expanded (see =t3-code-thinking-display=).

=RET= visits the file reference at point (=path:12:3=, =path#L12=, Markdown
links, the path of an =edit= block) in another window, or browses a URL;
=C-u RET= inverts the window choice; remote (TRAMP) names are never
followed.  On a pending question, =RET= answers it in the minibuffer, one
choice per prompt for multi-select questions (an empty answer finishes); on
an attention entry it reveals the request; elsewhere it toggles the block.  =!= runs a shell command on the file at point: an
isolated =*= marks where the file goes, otherwise it is appended, and a
trailing =&= runs asynchronously.

The chat follows new output; reading history stops following and =G=
resumes it.  Streaming updates preserve point and window positions.  Only a
recent window is loaded at first: =o= (or =RET= on the "Older history" line)
loads earlier pages.  Pending approvals, questions and failures are listed at
the top of the chat regardless of folding.

** Threads

The ledger (=C-c C-b=, =M-x t3-code-ledger=) lists every thread by project,
with pinned threads first, settled threads in a collapsed menu at the bottom
and delegated agents below their parent.  =^= marks pinned, =•= unseen and
=z= snoozed threads.  In the ledger, =RET= opens, =N= starts a thread in the
project at point, =+= pins, =v= archives, =/= searches, =j= switches, =r=
resumes, =s= toggles settled threads and =g= refreshes (=C-u g= restarts the
bridge).

=C-c C-j= switches to any active thread with completion, grouped by project.
=C-c C-r= resumes a settled or archived thread of the current project
(archived threads are restored first) and
=M-x t3-code-search-threads= searches titles and messages.

=C-c C-n= starts a thread: it asks where to work (project root, a new
worktree from a base ref, or an existing worktree) and opens an input whose
first =C-c C-c= launches the thread.  It inherits the current thread's model
and modes; =C-u C-c C-n= picks the project and model.

=f= in the chat forks the conversation at the turn at point (=C-u f= from
the latest point) and opens the fork.

Threads that finish, fail or need attention while not visible are announced
in the echo area; set =t3-code-notify= to =desktop= for desktop
notifications.  Opening a thread marks it seen.

** Common keys

| Key                | Context | Action                                       |
|--------------------+---------+----------------------------------------------|
| =C-c C-c=          | input   | Send, or queue while the thread is working   |
| =C-c C-s=          | input   | Steer the running turn                       |
| =C-c C-q=          | input   | Manage queued messages                       |
| =C-c C-k=          | both    | Abort the running turn                       |
| =C-c C-p=          | input   | Thread menu (=?= or =.= in the chat)         |
| =C-c C-m=          | both    | Select provider, model and options           |
| =C-c C-t=          | both    | Cycle reasoning effort                       |
| =C-c C-y=          | both    | Copy the last assistant message              |
| =C-c C-n=          | both    | New thread                                   |
| =C-c C-r=          | both    | Resume a settled or archived thread          |
| =C-c C-j=          | both    | Switch thread                                |
| =C-c C-b=          | both    | Ledger                                       |
| =M-p= / =M-n=      | input   | Prompt history (=C-r= to search)             |
| =TAB=              | input   | Complete commands, skills, files and paths   |
| =M-<next/prior>=   | input   | Scroll the chat                              |
| =TAB=              | chat    | Fold the tool block, thinking, or turn       |
| =S-TAB=            | chat    | Switch conversation / outline view           |
| =RET=              | chat    | Visit file or URL, answer, inspect, or fold  |
| =!=                | chat    | Shell command on the file at point           |
| =n= / =p=          | chat    | Next / previous user message (=M-g i= index) |
| =f=                | chat    | Fork at the turn at point                    |
| =o=                | chat    | Load older history                           |
| =i= / =m= / =a=    | chat    | Focus the input (=a= at its end)             |
| =G=                | chat    | Jump to latest and follow                    |
| =M-w= / =C-u M-w=  | chat    | Copy visible / raw text                      |
| =q=                | chat    | Hide the chat and input windows              |

The thread menu also offers approvals (=y=, =Y=, =x=, =X=), answering or
dismissing questions (=a=, =A=), queued messages (=Q=, also =C-c C-q= in the
input: edit, cancel, steer now, reorder, resume), explicitly queued sends
(=q=), runtime and plan modes, rename (=C-u N= regenerates the title), pin,
settle, snooze, archive and delete, the worktree in Dired, VC status, and
copying IDs.  A send mode chosen from the menu (steer, restart) is shown in
the input header until the next send.  Queued messages too long for the
bridge to send in full cannot be edited, only cancelled and resent.

** Hooks

=t3-code-activity-phase-functions= runs with =(CHAT INPUT OLD NEW)= when a
thread's phase changes between ="idle"=, ="thinking"=, ="replying"=,
="running"= and ="waiting"=.  =t3-code-shell-update-functions= runs with
=(ENVIRONMENT OLD NEW)= shell payloads.

* Limits

The bridge keeps payloads below Emacs's 1 MiB line limit: the live window
holds the 100 most recent items and a bounded amount of text, and history
pages have the same bounds.  Search and outline cover loaded content only.
Arbitrary dynamic-tool input/output is omitted at the bridge because it may
contain credentials.  Command output is shown in the transcript, not as a
live terminal.  Hiding or killing a view never stops server work.

* Development

make check            # byte-compile and ERT, using the fake bridge
make check-t3code     # also the adjacent T3 bridge's tests and real startup
#+end_src

See [[file:docs/protocol-v1.md][the protocol v1 specification]].

* Compatibility policy

The bridge handshake reports its own version, pinned T3 revision, server
version, environment identity, and capabilities.  Emacs never decodes raw
Effect RPC; it offers features only when the bridge advertises them
(=modelSelection=, =threadLifecycle=, =composerCompletion=).
